# 游戏汉化工程可复用框架设计

## 1. 设计目标

将一次完整的游戏汉化流程拆分成可独立维护、测试和复用的工程模块。

核心原则：

- 通用能力与游戏专属逻辑分离。
- 原始资源只读，修改在隔离目录进行。
- 每个文本槽具有稳定的唯一标识。
- 翻译、编译、部署、实机验收分别管理。
- 所有文件变更可追踪、可校验、可恢复。
- 失败时停止并保留诊断信息，不静默跳过错误。

## 2. 推荐架构

```text
Game Localization Toolkit
│
├── Extraction Layer
│   ├── 游戏脚本解析
│   ├── 文本槽识别
│   └── 原始结构保存
│
├── Translation Layer
│   ├── AI 模型适配
│   ├── 术语表管理
│   ├── 上下文组织
│   └── 翻译结果写回
│
├── Validation Layer
│   ├── 文本槽一致性
│   ├── 脚本结构校验
│   ├── 字体与编码检查
│   ├── 编译结果校验
│   └── SHA-256 校验
│
├── Deployment Layer
│   ├── 文件白名单
│   ├── 独立备份
│   ├── 安全替换
│   ├── 事务日志
│   └── 自动回滚
│
└── Release Layer
    ├── 最终成果汇总
    ├── Manifest 生成
    ├── 补丁打包
    └── 安装与恢复说明
```

## 3. 应优先保留的核心框架

### A. 文本槽提取框架

**用途：** 从游戏脚本中准确识别需要翻译的内容。

应保留：

- 原始脚本解析器。
- 文本槽分类规则。
- 全局唯一槽 ID 生成方法。
- 原始行号和上下文记录。
- 文本替换及写回逻辑。
- 未识别文本的异常报告。

推荐通用数据结构：

```json
{
  "slot_id": "script_001:000123",
  "script": "script_001",
  "line": 123,
  "type": "dialogue",
  "source_language": "ja",
  "source_text": "示例原文",
  "target_language": "zh-CN",
  "translated_text": "示例译文",
  "status": "translated"
}
```

注意：这是下一项目可采用的示例结构，不代表本项目已有工具使用完全相同的字段。

### B. AI 翻译框架

**用途：** 将文本槽、上下文和术语约束统一交给模型处理。

应保留：

- 模型调用接口。
- 翻译提示词模板。
- 术语注入机制。
- 分批处理逻辑。
- API 失败重试。
- 翻译结果缓存。
- JSON 输出解析。
- 翻译质量检查规则。

翻译约束：

1. 日文原文优先。
2. 英文作为辅助参考。
3. 不增加原文不存在的信息。
4. 保留人物语气及原文歧义。
5. 不修改脚本控制代码。
6. 专有名词遵循术语表。

建议把模型供应商、API 密钥、批次大小和重试次数做成配置，而不是写死在程序中。

### C. 术语表框架

**用途：** 保证跨章节、跨批次的翻译一致性。

应支持：

- 标准译名。
- 原文别名。
- 英文参考名。
- 使用范围。
- 禁止使用的错误译名。
- 术语冲突检测。
- 版本管理。

术语表必须与游戏的编译索引分离。

### D. 编译与静态验证框架

**用途：** 在游戏运行之前发现脚本损坏或不兼容问题。

应保留：

- 原始文件往返编译检查。
- 文本槽数量和标识校验。
- 调用签名与参数检查。
- 控制结构与行表检查。
- MGSC v1 格式校验。
- 字体及缺字检查。
- 原始文件与目标文件哈希比对。

其中 MGSC v1 是本项目的游戏专属格式，未来其他游戏应通过独立适配器接入。

### E. 安全部署与回滚框架

**用途：** 防止批量文件替换导致游戏损坏。

应保留：

- 部署 manifest。
- 路径规范化。
- 白名单校验。
- SHA-256 快照。
- 独立原版备份。
- 备份完整性验证。
- 安全文件替换。
- 事务日志。
- 部署后全目录审计。
- 失败自动回滚。

必须保留的回归测试：

- File.Replace 备份路径为空。
- 部署清单与快照路径根不一致。
- 中文及空格路径。
- 白名单外文件被修改。
- 部分文件部署成功后发生失败。
- 备份损坏或缺失。
- 回滚后哈希不一致。
- 路径逃逸与重解析点越界。

### F. 汉化覆盖包框架

**用途：** 将已验收的文件整理成可重复安装的补丁。

应保留：

- 多批次成果合并。
- 文件去重与冲突检查。
- 最终文件哈希清单。
- 相对路径映射。
- ZIP 打包与完整性检查。
- 安装前版本兼容性检查。
- 原版恢复说明。

本项目最终覆盖包包含 86 TXT、86 MG 和 1 份编译索引，共 173 个文件。

此数字是本项目的实际结果，不应成为框架中的固定配置。

## 4. 通用模块与专属模块的边界

| 模块 | 复用程度 | 说明 |
|---|---|---|
| SHA-256 文件审计 | 高 | 基本不依赖游戏 |
| 事务部署与回滚 | 高 | 需要配置目标路径 |
| Manifest 生成 | 高 | 文件结构可配置 |
| AI 翻译接口 | 高 | 可替换模型供应商 |
| 术语表管理 | 高 | 数据因项目而异 |
| 批次进度管理 | 高 | 适合多数汉化项目 |
| 文本槽解析 | 中 | 需适配脚本语法 |
| 字体映射 | 中 | 需适配游戏引擎 |
| MGSC v1 编译 | 专属 | 依赖当前游戏格式 |
| Kakera 解锁映射 | 专属 | 不能迁移到其他游戏 |

## 6. 下一项目的标准流程

1. 建立只读原始游戏基线。
2. 编写或选择游戏脚本适配器。
3. 运行最小规模文本提取测试。
4. 验证中文字体与脚本编译。
5. 建立术语表和翻译提示词。
6. 分批翻译并保存状态。
7. 编译和自动校验。
8. 部署到隔离测试副本。
9. 按正常游戏流程验收。
10. 冻结成果并制作覆盖包。
11. 备份正式游戏后安装测试。
12. 归档版本及技术复盘。

## 7. GitHub 代码保留原则

应上传：

- 自行编写且有权公开的工具代码。
- 不含受保护游戏内容的配置模板。
- 合成测试脚本与测试数据。
- 通用翻译提示词。
- 技术说明和故障案例。
- 自动化测试代码。

不应默认上传：

- 游戏原版 TXT/MG。
- 完整汉化脚本及编译资源。
- 游戏可执行文件或资源包。
- 用户存档。
- API 密钥。
- 未经授权再分发的第三方编译器。

## 8. 后续开发优先级

**P0：** 保存并验证现有可复用代码、部署脚本及测试用例。

**P1：** 抽象统一的文本槽、术语表和 manifest 数据结构。

**P2：** 实现可替换的游戏脚本适配器。

**P3：** 将翻译、编译、校验、部署、打包整合成统一命令行工具。

最终目标是让下一次汉化项目主要完成游戏适配和翻译工作，而不需要重新开发完整工程基础设施。
