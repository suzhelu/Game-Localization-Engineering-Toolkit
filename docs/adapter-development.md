# Developing text adapters

## Existing contract and audit findings

`localization_toolkit.models.TextSlot` is the game-independent slot record. It carries a stable `slot_id`, category/role, source and target text, source offsets, line/column, call/argument location and optional speaker/context. `ExtractionResult` binds slots to source SHA-256, issues, controls and an adapter-owned payload. `TextAdapter` currently requires `extract(source, script, reference_source=None)` and `write(parsed, translations)`.

The existing `BgiAdapter` public surface includes `extract`, `write`, schema records (`TextPair`, `CallSchema`, `OpaqueCallSchema`) and lexer/literal helpers. Its lexer preserves offsets and fails on malformed delimiters/literals. Unknown string calls, unresolved menus and dynamic formatting calls report issues that block writeback. `write()` requires an exact slot-ID set and preserves all non-target tokens, calls, arguments, controls and source bytes. Slot IDs are generated by `_make_slot` from script key, call/argument address, role and source-language text (plus menu item identity where applicable); replacement target text is not part of the ID. Batch B does not change that algorithm.

Safe translation writeback remains in `translation.workflow.write_approved()`: it verifies current source/context/rule fingerprints and explicit human approval, then calls the chosen adapter's `write()`. Compilation consumes the general `TextAdapter` through `compilation.reviewed`; it does not import BGI. The finite MGSC v1 validator is not an adapter requirement. CLI previously instantiated `BgiAdapter` in `cli.workflow._adapter` and rejected any other ID in `cli.config.Project.validate`. This batch replaces those two points with the registry; existing `general.adapter: "bgi"` and `game_specific.adapter_options` stay valid.

## Registry API

`localization_toolkit.adapters.AdapterRegistry` accepts an `AdapterDescriptor` and a factory taking a mapping of game-specific options. An adapter instance declares matching `adapter_id`, `version`, `formats`, and `capabilities`, and implements `probe`, `extract`, and `write`. Required declarations are `extract`, `writeback`, and `format_probe`. Optional `format_validate` is accepted only if the instance implements `validate_format(source) -> FormatValidation`; callers invoke it through `registry.validate_format(id, source, options)`. The registry checks metadata/method presence and validates the returned evidence record; tests must still prove behavior. A declaration by itself is not evidence that a capability works.

```python
from localization_toolkit.adapters import AdapterDescriptor, AdapterRegistry, BgiAdapter

registry = AdapterRegistry(discover_plugins=False)
descriptor = AdapterDescriptor("bgi", BgiAdapter.version, BgiAdapter.formats,
                               BgiAdapter.capabilities, "Explicit-schema BGI source")
registry.register(descriptor, lambda options: BgiAdapter.from_options(options))
adapter = registry.create("bgi", {})
result = adapter.extract('OutputLineAll("synthetic source", "synthetic target", 0);', "demo")
```

`default_registry()` registers BGI and discovers Python entry points in group `localization_toolkit.adapters`. An entry-point name is the adapter ID; its loaded callable receives the registry and must register exactly one adapter with that ID. Discovery reads metadata; the module is imported only when the configured ID is selected. Selecting an installed plugin executes its Python code in-process. Install and select only code the operator trusts. Unknown IDs fail; there is no fallback to BGI.

Project config keeps `general.adapter` and `game_specific.adapter_options`. The CLI's `localize adapters` reports loaded descriptors and separately lists discovered plugin IDs not loaded. `localize adapters --load ID` explicitly loads one trusted plugin and shows its declared metadata/capabilities. For a plugin, use `localize probe FILE --adapter ID` or `localize probe FILE --project PROJECT`; the latter uses its configured ID/options. By default automatic probing checks registered built-ins only. `localize probe FILE --include-plugins` loads every discovered plugin to check for ambiguous matches; this executes all those installed hooks, so use it only when each plugin package is trusted. The registry reports ambiguity whenever multiple loaded adapters return `supported`.

## Read-only probe rules

`probe(source)` receives decoded text and returns `FormatProbe` with `supported`, `unsupported`, or `needs_confirmation`, plus evidence. The registry reports multiple supported matches as `ambiguous`. A probe must not execute files, modify them, or infer support from extensions. It is advisory: `extract()` and unresolved-structure checks remain authoritative before writeback. CLI input currently requires UTF-8; binary formats need their own safe inspection design.

The BGI probe uses lexer/call syntax and a configured visible-text schema. A recognized call proves only that the supported source subset appears; it does not prove every call is understood or safe to write. Unknown string calls still block through extraction. File names and extensions are never sufficient evidence.

## New adapter template

Copy `examples/adapters/template/` into a separately maintained adapter project. It implements only `SYNTHETIC-TEXT-V1`, a small line-based fixture. Run from the repository root:

```powershell
$env:PYTHONPATH = 'src'
python -m unittest examples.adapters.template.test_adapter -v
```

The tests cover extraction, byte-identical unchanged writeback, text-only replacement, malformed-input rejection, duplicate IDs and capability claims. `tests/test_adapter_registry.py` exercises entry-point selection into the existing CLI extraction stage and the existing unreviewed-writeback gate. This fixture is training material, not a game format.

Preserve bytes outside identified text spans, reject unknown structures, require exact slot maps, retain source-derived IDs, and re-extract output to compare slot order and control signatures. Add format-specific synthetic tests. A parser warning never authorizes writing.

## Limits and concurrency

Text adapters do not need to compile scripts, rebuild resources, or validate binary output. Those are separate compiler/artifact interfaces. Translation remains local Mock-only; human review remains mandatory.

`TranslationStore` is an atomic local JSON file without an interprocess lock or conflict detection. Use one writer per state file. Batch B does not add locking: current commands are synchronous and this extension does not require parallel writes. If future Agent orchestration adds concurrent workers, first design a storage protocol/lock or optimistic revision check and test process-level contention; do not share one store across concurrent writers.

Probing and static checks do not establish in-game behavior. Real deployment needs explicit authorization, pinned files, a verified backup and the transaction workflow. Do not include game content, secrets or unauthorized compilers in adapter packages.
